# DECISIONS — 주요 결정과 이유

> 새 결정은 아래 형식으로 **맨 아래에** 추가한다. 번복할 때는 지우지 말고 새 항목을 만들고 이전 항목 상태를 "대체됨(D-0xx)"으로 바꾼다.
>
> ```
> ## D-0xx. 제목 (YYYY-MM-DD) — 상태: 확정 | 검토 중 | 대체됨
> - 결정:
> - 이유:
> - 대안:
> ```

## D-001. 웹캠 기반 비접촉 방식 (2026-11-02) — 상태: 확정
- 결정: 센서·스마트 베드 대신 **웹캠 + AI 비전**으로 자세를 인식한다.
- 이유: 환자 피부 접촉·소모품·소독 문제가 없고, 침대 교체 비용(수백만 원)이 들지 않는다.
- 대안: 웨어러블 IMU 센서(정확하지만 부착 부담), 압력 매트(비쌈).

## D-002. 영상은 엣지에서만 처리, 서버엔 좌표·라벨만 (2026-11-02) — 상태: 확정
- 결정: 병상 PC(edge)에서 추론하고, 서버로는 자세 라벨·신뢰도·관절 좌표·시각만 보낸다. 원본 프레임은 저장하지 않는다(`SAVE_RAW_FRAMES=false`).
- 이유: 환자 신체 촬영은 민감한 개인정보다. 영상이 밖으로 나가지 않으면 유출 위험과 동의 부담이 크게 줄어든다. 대역폭도 절약된다.
- 대안: 서버에서 영상 스트림 처리 (GPU 한 곳에 모을 수 있으나 프라이버시 위험 큼).

## D-003. "진단"이 아닌 "기록·알림 보조" (2026-11-02) — 상태: 검토 중
- 결정: 서비스 문구와 기능을 체위변경 **기록·알림 보조**로 한정한다. 욕창 발생 예측·진단 표현을 쓰지 않는다. 3D 히트맵은 "유지 시간 기반 추정"임을 표시한다.
- 이유: 진단 보조로 보이면 의료기기 소프트웨어 허가 대상이 될 수 있다.
- 남은 일: 식약처 의료기기 해당 여부 확인 (공모전 이후 사업화 단계).

## D-004. 포즈 추정은 MediaPipe 기본, YOLO는 라이선스 확인 후 (2026-11-02) — 상태: 확정
- 결정: MVP 포즈 추정기는 **MediaPipe Pose (Apache 2.0)**. `PoseEstimator` 인터페이스 뒤에 두어 교체 가능하게 한다.
- 이유: 기획서는 YOLOv8-pose를 추천했지만 Ultralytics YOLO는 **AGPL-3.0**이라 상용 서비스에 쓰려면 소스 공개 또는 유료 라이선스가 필요하다. MediaPipe는 CPU에서도 빠르다.
- 대안: YOLOv8/11-pose (이불·가림에 강할 수 있음 → 정확도 비교 후 라이선스 구매 검토), RTMPose(Apache 2.0, MMPose).

## D-005. Python 3.11 고정 (2026-11-02) — 상태: 확정
- 결정: backend·edge 모두 Python 3.11.
- 이유: MediaPipe·OpenCV 휠 호환이 가장 안정적이고, 팀원 환경을 맞추기 쉽다.

## D-006. MVP 자세 분류는 규칙 기반 (2026-11-02) — 상태: 확정
- 결정: 관절 좌표 기하 규칙으로 5가지 자세를 분류하고, 정확도가 목표(90%)에 못 미치면 keypoints 기반 경량 분류기로 바꾼다.
- 이유: 학습 데이터 없이 바로 시작할 수 있고 결과를 설명하기 쉽다.

## D-007. 체위변경 기준 120분, 설정값으로 관리 (2026-11-02) — 상태: 확정
- 결정: 기본 120분(경고 100분), 환자별로 다르게 설정 가능 (`patients.reposition_interval_min`).
- 이유: 2시간이 일반 수칙이지만 환자 상태·매트리스에 따라 병원이 다르게 정한다.

## D-008. 실시간 전달은 WebSocket + 웹 푸시 (2026-11-02) — 상태: 대체됨(D-011)
- 결정: 대시보드는 WebSocket, 스마트폰은 웹 푸시(PWA). 네이티브 앱은 만들지 않는다.
- 이유: 앱 설치 없이 병원 PC·간호사 폰에서 바로 쓸 수 있고 개발 범위가 작다.

## D-009. DB는 Supabase(PostgreSQL), 서울 리전 (2026-11-04) — 상태: 확정
- 결정: PostgreSQL을 직접 설치하지 않고 **Supabase 클라우드**(서울 `ap-northeast-2`)를 쓴다. Redis는 쓰지 않는다.
- 이유: 설치 없이 바로 쓰고, 로그인(Auth)·권한(RLS)·실시간 전달(Realtime)이 함께 제공된다. 관리자·간호사·보호자가 어디서든 같은 데이터를 본다. 셀프 호스팅도 가능해 병원 내부 설치 요구에 대응할 수 있다.
- 대안: SQLite(시연은 쉽지만 여러 사람이 원격 접근 불가), 직접 설치한 PostgreSQL + Redis(운영 부담 큼).
- 주의: Supabase에도 영상은 올리지 않는다(D-002). Postgres 버전은 클라우드 기본값을 따르고, 로컬은 `supabase/config.toml`의 `major_version`으로 맞춘다.

## D-010. FastAPI 백엔드는 유지, Supabase는 데이터·로그인·실시간 담당 (2026-11-04) — 상태: 확정
- 결정: edge 이벤트 수신, 타이머·알림 판단, 압박 누적 계산, 문자 발송, 기기 토큰은 **FastAPI**가 맡는다. FastAPI는 service key로 Supabase에 쓰고, 화면은 Supabase에서 읽는다.
- 이유: 알림 판단이 이 서비스의 핵심 로직이라 edge와 같은 Python으로 짜고 pytest로 테스트하기 쉬운 곳에 둔다.
- 대안: Supabase만 사용(Edge Functions·pg_cron). 서버 코드는 줄지만 TypeScript로 나뉘고 테스트가 어렵다.

## D-011. 로그인은 Supabase Auth, 실시간은 Supabase Realtime (2026-11-04) — 상태: 확정
- 결정: 자체 JWT 로그인과 FastAPI WebSocket을 만들지 않는다. 로그인은 **Supabase Auth**(이메일), 권한은 **RLS**, 대시보드 실시간 갱신은 `bed_status`·`alerts` 테이블 **Realtime 구독**으로 한다. FastAPI는 Supabase가 발급한 JWT를 검증해 사용자를 확인한다. 스마트폰 알림은 그대로 웹 푸시(PWA)이며 네이티브 앱은 만들지 않는다.
- 이유: 직접 만들 코드가 줄고, 권한 규칙이 DB에 있어 화면·API 어디서 읽어도 같은 범위만 보인다.
- 대안: FastAPI JWT + WebSocket(D-008 원안).

## D-012. 알림은 3단계: 대시보드 → 웹 푸시 → 문자 (2026-11-04) — 상태: 확정
- 결정: ① 간호스테이션 대시보드 깜빡임·반복 경고음(확인할 때까지), ② critical 시 스마트폰 웹 푸시, ③ `ALERT_ESCALATE_MIN`(기본 5분) 동안 아무도 확인하지 않으면 문자 발송.
- 이유: 브라우저 소리는 놓치기 쉽고, iOS 웹 푸시는 16.4 이상 + 홈 화면 추가 시에만 동작해 단독으로 믿기 어렵다.
- 대안: 카카오 알림톡(더 싸지만 사업자 등록·템플릿 승인 필요 → 사업화 단계), 네이티브 앱 푸시(iOS 신뢰도가 실제 문제가 될 때 검토).
- 남은 일: 문자 API 업체·단가 확인.

## D-013. 카메라 위치와 분류 방식 (2026-11-04) — 상태: 검토 중
- 결정: 1주차 인식 검증(TASKS T1-0) 결과로 정한다. 후보 위치는 천장(바로 위), 발치 위 45°, 침대 옆 위 45°.
- 판단 기준: 사람 검출률 ≥ 90%면 규칙 기반(D-006) 유지. 측위(30° 포함)만 약하면 위치 변경 + scikit-learn 분류기. 전반적으로 낮으면 RTMPose 비교.
