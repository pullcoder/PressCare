# SECURITY — 개인정보 · 비밀값 보호 기준

> 2026-11-04 작성. 환자·보호자·간호사 정보를 다루므로 **이 문서의 규칙은 기능보다 우선한다.**
> 관련 결정: D-002(영상 미전송), D-014(JWKS 검증), D-015(필드 암호화), D-016(비밀값 해시)

## 1. 원칙

1. **안 모으면 안 샌다.** 꼭 필요한 정보만 저장한다. 환자 실명·주민번호·영상은 저장하지 않는다.
2. **평문은 backend 메모리 안에서만.** 개인정보는 DB에 암호문으로 저장하고, backend가 권한을 확인한 뒤에만 복호화한다.
3. **비밀값은 되돌릴 수 없게.** 비밀번호·토큰은 해시로만 저장한다.
4. **키는 코드와 분리.** 모든 키는 `.env`(운영은 호스팅 서비스의 비밀값 설정)에만 두고 커밋하지 않는다.
5. **로그에 남기지 않는다.** 개인정보·토큰·복호화한 값은 로그·에러 메시지·분석 도구로 보내지 않는다.

## 2. 데이터별 보호 방식

| 데이터 | 저장 위치 | 보호 방식 | 비고 |
|--------|----------|----------|------|
| 로그인 비밀번호 | Supabase Auth (`auth.users`) | **Supabase가 해시(bcrypt)로 저장** | 우리 서버는 비밀번호를 받지도 저장하지도 않는다. 화면 → Supabase Auth로 바로 전송 |
| 우리가 직접 저장하는 비밀값 (예: 보호자 화면 PIN, 관리자 2차 비밀번호) | 우리 DB | **Argon2id 해시** (4장) | MVP에는 없음. 생기면 반드시 이 방식 |
| 엣지 기기 토큰 | `edge_devices.token_hash` | **SHA-256 해시** | 발급 응답에서 1회만 보여줌. 무작위 32바이트라 Argon2id 불필요 (4장) |
| 휴대폰 번호 | `profiles.phone_enc`, `phone_bidx` | **AES-256-GCM 암호화** + HMAC 검색 인덱스 | 저장 전 숫자만 남겨 정규화 (`01012345678`) |
| 연락용 이메일 | `profiles.contact_email_enc`, `contact_email_bidx` | **AES-256-GCM 암호화** + HMAC 검색 인덱스 | 소문자로 정규화 |
| 주소 | `profiles.address_enc` | **AES-256-GCM 암호화** | 검색하지 않으므로 인덱스 없음 |
| 로그인 이메일 | Supabase Auth (`auth.users.email`) | Supabase 관리 (평문) | 로그인에 필요해 암호화할 수 없다. RLS로 본인·관리자만 조회 |
| 환자 표시 이름 | `patients.display_name` | 가명·이니셜만 (`이○○`) | 실명 저장 안 함 |
| 병상 영상 | 저장 안 함 | 병상 PC 메모리에서만 처리 | D-002 |
| 관절 좌표·자세 기록 | `posture_events` | 평문 + RLS | 개인 식별 불가 |
| 사용자 세션 토큰 (JWT) | 브라우저 (supabase-js) | ES256 서명, 짧은 만료, JWKS 검증 | 로그·URL에 넣지 않음 (D-014) |
| 웹 푸시 구독 정보 | `push_subscriptions` | 평문 + RLS (본인만) | 유출 시 구독 삭제로 무효화 |

> 새 개인정보 컬럼을 만들 때는 이 표에 먼저 추가하고 PR에서 리뷰받는다.

## 3. 필드 암호화 (AES-256-GCM)

- 라이브러리: Python `cryptography`의 `AESGCM`. 직접 암호 알고리즘을 구현하지 않는다.
- 키: `FIELD_ENCRYPTION_KEY` (32바이트, base64).
- 암호화할 때마다 **새 12바이트 무작위 nonce**를 만든다. 같은 nonce를 재사용하지 않는다.
- 저장 형식 (`bytea`): `키 버전(1바이트) ‖ nonce(12) ‖ 암호문 ‖ 인증 태그(16)`
- AAD(추가 인증 데이터)에 `테이블:컬럼:행 id`를 넣는다. 다른 행의 암호문을 복사해 붙여도 복호화가 실패한다.
- 검색용 인덱스: `HMAC-SHA256(BLIND_INDEX_KEY, 정규화한 값)`. 정확히 같은 값 찾기만 가능하다(부분 검색 불가).
- 코드는 `backend/app/core/crypto.py` 한 곳에 모으고, 다른 곳에서 직접 암호화·복호화하지 않는다.
- 테스트: 암호화→복호화 왕복, 다른 행 AAD로 복호화 실패, 같은 값을 두 번 암호화하면 암호문이 다름.

## 4. 해시 (Argon2id · SHA-256)

### 사람이 정한 비밀값 → Argon2id
- 라이브러리: `argon2-cffi`의 `PasswordHasher`.
- 파라미터 최소값 (OWASP 권장): 메모리 19 MiB(`memory_cost=19456`), 반복 2(`time_cost=2`), 병렬 1(`parallelism=1`).
- 결과는 파라미터가 포함된 문자열(`$argon2id$v=19$m=...`) 그대로 저장한다.
- 로그인 성공 시 `check_needs_rehash()`가 참이면 새 파라미터로 다시 해시한다.
- 로그인 비밀번호는 Supabase Auth가 관리하므로 **우리가 Argon2id로 다시 해시하지 않는다.** Supabase 대시보드의 Auth 설정에서 최소 길이(10자 이상)와 문자 조합 규칙을 켠다.

### 무작위로 만든 토큰 → SHA-256
- 엣지 기기 토큰처럼 서버가 `secrets.token_urlsafe(32)`로 만든 값은 추측이 불가능하므로 SHA-256 해시로 충분하다.
- 매 요청마다 검증해야 해서, 일부러 느린 Argon2id를 쓰면 서버가 느려진다.
- 비교는 `hmac.compare_digest`로 한다 (시간 차 공격 방지).

## 5. 키 관리

| 키 | 용도 | 누가 가짐 |
|----|------|----------|
| `SUPABASE_SERVICE_ROLE_KEY` (secret 키) | backend → DB 쓰기 (RLS 무시) | backend 담당 |
| `FIELD_ENCRYPTION_KEY` | 개인정보 암호화 | backend 담당 |
| `BLIND_INDEX_KEY` | 검색 인덱스 | backend 담당 |
| `WEB_PUSH_VAPID_PRIVATE_KEY` | 웹 푸시 발송 | backend 담당 |
| `SMS_API_SECRET` | 문자 발송 | backend 담당 |
| `EDGE_DEVICE_TOKEN` | 병상 PC 인증 | 해당 병상 PC만 |

- 생성은 한 명이 하고 팀 비공개 채널로 전달한다. 메신저 대화방에 오래 남기지 말고 전달 후 삭제한다.
- **개발과 운영은 다른 키**를 쓴다. 운영 키는 호스팅 서비스(Render, Vercel 등)의 비밀값 설정에만 넣는다.
- 암호화 키를 잃으면 데이터를 복구할 수 없다. 운영 키는 안전한 곳(비밀번호 관리자 등)에 별도 백업한다.
- 키 교체: 새 키를 다음 버전 번호로 추가 → 읽을 때 저장된 버전으로 복호화 → 새로 쓸 때 새 버전으로 암호화 → 배치 작업으로 전체 재암호화 → 옛 키 폐기.

## 6. 전송·접근

- 모든 통신은 HTTPS. edge → backend도 HTTPS만 허용한다 (로컬 개발 제외).
- `CORS_ORIGINS`는 실제 프론트 주소만 넣는다. `*` 금지.
- 모든 테이블에 RLS를 켠다. 연락처 같은 암호화 컬럼은 화면에서 직접 읽지 않고 backend API가 역할을 확인해 복호화한다.
- 연락처를 복호화해 보여줄 때는 기본으로 가린다 (`010-****-5678`). 전체 보기는 필요한 역할만.
- v1: 개인정보 열람 기록(`access_logs`: 누가, 언제, 누구의 무엇을)을 남긴다.

## 7. 로그·에러

- 로그 금지: 휴대폰·이메일·주소(평문·암호문 모두), 토큰, `Authorization` 헤더, keypoints 원본, 환자 이름.
- 에러 응답에 내부 정보(SQL, 스택 트레이스, 키 이름)를 넣지 않는다.
- 꼭 필요하면 마스킹해서 남긴다: `phone=010****5678`, `user_id`만.

## 8. 보관·삭제

- 환자가 퇴원하거나 보호자 연결이 끝나면 해당 연락처를 삭제한다.
- 자세 기록 보관 기간은 사업화 단계에서 병원 기준과 법률 검토로 정한다. ⚠️ 확인 필요
- 건강 관련 정보는 개인정보보호법상 민감정보로 볼 수 있다. 실제 병원 도입 전에 법률 검토와 개인정보 처리방침을 준비한다. ⚠️ 확인 필요
